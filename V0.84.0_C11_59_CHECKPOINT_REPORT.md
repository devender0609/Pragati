## E/F/G. The 91-vs-90 discrepancy — root cause

Not a typo, and not a misread denominator. **A generator run against a
transiently-broken catalogue.**

At checkpoint 102C the ledger was written from `arts.length` at a moment
when Chapter 12 still merged two authored modules and sorted by page, so
FO-11 appeared twice — 91 rows, 1 duplicate. The Chapter 12 filter was
fixed minutes later. **The ledger was never regenerated.**

The reason nobody caught it: the ledger ROWS key on artifact id, so the
duplicate collapsed and the rows stayed correct at 90 unique ids. Only the
top-level scalar carried the error, and it rode through a first-green
package and a hardened package.

Independently derived from the registry at this checkpoint:

| Source | Value |
|---|---|
| Registry entries | **90** |
| Unique `contentArtifactId` | **90** |
| Duplicates | **0** |
| Catalogue rows · unique | 90 · 90 |
| Ledger scalar (before) | **91** |
| Sum of unit→artifact references | **129** — not an artifact count |

That last row is the trap the rule exists for: 93 units reference
artifacts 129 times across 90 distinct lessons, because a source key can
carry several units.

## H/I. The repair

**The ledger had no generator.** It was written inline by checkpoint
scripting, which is precisely why it could drift — a hand-written file
cannot be regenerated after the model moves.

Added `tools/class11/generateCompletenessLedger.ts`, which derives every
scalar from the live model and counts **distinct artifact identities**,
never catalogue rows and never reference sums. Regenerated:
**`artifacts: 90`**, and the file now names its own generator.
