## B. Why SVG-only matching was invalid

The all-family harness defined a mathematical figure as
`svg[role=img]` with drawn primitives. That is a statement about rendering
technology, not about mathematics, and two families are semantic HTML on
purpose:

- **proof_layout** — five real headings, so the argument survives without
  colour, indentation or vector graphics
- **arrangement** — a `figure` containing an `<ol>`, because a list of
  arrangements is a list

Both reported **0** and both were in fact rendering. A false negative about
the product, produced by a test that encoded one implementation choice as if
it were the definition.

## C. The general fix

One hook at the dispatcher, not a special case per family. Every visual is
wrapped in `[data-visual-kind={spec.type}]` with `display: contents`, so it
adds identity and no layout. All twelve families gained it from a single
change.

The harness now finds the family root **by kind**, then checks content that
fits that family — primitives for drawn figures, cells for tables, entries
for lists, headings for proofs. A root with no content does not count, so a
matching empty container still fails.

Decorative icons carry no visual-kind root and are excluded structurally
rather than by subtraction: 11 to 14 icons per page, none counted.

Accessibility is checked per family too. Semantic HTML is **not** made to
impersonate an image to satisfy the harness — headings are accessibility
structure in their own right.
