## §A — the review system could only see one chapter

The packaging apparatus imported `fractionsChapterSections()` and
`authoredSectionById()` straight from `fractionsChapter.ts`. Both names
say "fractions" and both were the only way in, so package generation,
fingerprinting, the reviewer questions and the readiness assessment
could each see exactly one chapter.

Invisible while Fractions was the only authored chapter. The moment
Number Play was written it became content with **no route to a
reviewer** — work the system did not know existed and would therefore
never report as waiting. A backlog you cannot see is worse than a long
one.

`authoredSections.ts` is now the single registry. Chapters stay
**separable**, because a reviewer reads a chapter and not a product:
every function takes or reports a chapter, and the scope is a parameter
instead of a hard-coded import. A test walks the authored sections and
fails if a chapter with content is missing from the registry, so this
cannot recur silently.

**A second instance of the same bug** sat in the completeness assessor,
which counted only the Fractions misconception registry — so a Number
Play section with four documented misconceptions was assessed as having
none. Fixed the same way.

## §B — §3.3 Patterns of Numbers on the Number Line

Authored on the **existing** `NumberLineSpec`. Whole numbers are written
as `ExactFraction` with denominator 1, so the same renderer serves both
this and §7.4 — the right reuse, as against a parallel integer line that
would then drift.

Three visuals: counting in tens (constant step, even spacing), 10-20-60
(adjacent in a list, far apart on the line), and doubling (growing step,
widening gaps). The middle one is the section's hinge and is marked
`expose_misconception`.

Three new misconceptions, all about reading **distance** rather than
about the numbers. Two carry a diagnostic signal;
`position_read_from_label_not_length` carries `null`, because a single
answer cannot show whether a student measured or guessed from the label
order.

§3.3 was drawable in v0.79 and was deliberately left until §3.2 was
done, because §3.2 comes first in the book. The test pinning the
authored list to book order is what enforced that.

## §C — what §3.4 needs, specified and NOT built

**§3.4 Playing with Digits** (p. 60) treats a number as a sequence of
digits in places: the 7 in 736 is seven hundreds, and rearranging the
digits makes a different number.

Nothing in the current spec union can express that. A number line places
a number as a **point** and a number grid places it in a **cell** — both
treat the number as atomic, which is the exact opposite of what this
section is about.

**Required: `PlaceValueSpec`.** It must hold
- the digits in order, and the place each occupies;
- which places are named (ones, tens, hundreds) — the source uses at
  least three, and a spec that hard-codes three will break at Class 7;
- optional emphasis on one digit or one place, for "what is the 7
  worth here?";
- optional paired display of two numbers built from the same digits, for
  rearrangement.

**It must not hold** the value of a digit in its place. That is
derivable — digit × place value — and storing it would let a caption and
a diagram disagree, which is the failure the fraction-strip schema was
rewritten in v0.61 to eliminate and the reason `supercellsFor()` computes
rather than stores.

Renderer needs: a place-value column or block diagram, with the same
accessibility treatment `NumberGridFigure` uses — a visually hidden
table, because a screen reader given a flat list of digits learns
nothing about place, which is the mathematical content.

Not built. Specifying it here rather than discovering it mid-authoring
is the point of §C.
