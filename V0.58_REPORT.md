## 3. Framework gate — the critical fix

`prepareGrowthAdministration()` now runs the full chain, with framework
approval **first**:

> evidence → human review → framework approved → specification approved
> → grade permitted → context → item eligibility → assembly

**Why first matters:** items are tagged to domains the framework
defines. v0.57 would have assembled a perfectly balanced form against a
blueprint nobody had agreed to. A test proves 60 flawless items produce
no form without approval, and that the gate fires *before* item checks —
`rejected` is empty because it never gets that far.

## 4. Specification lifecycle

Five states; only `approved_for_field_test` may create an assignment.
`PILOT_ADMINISTRATION_V1` remains `draft` and is **refused for
administration while staying fully usable for simulation, assembler
tests, and bank planning** — which is what a research hypothesis is for.

## 5. Unresolved constructs

`ResearchBlueprintHypothesis` vs `ApprovedFieldTestBlueprint`. The
approved blueprint is generated **from** a frozen framework version,
never the reverse. Unresolved constructs are recorded explicitly rather
than silently stripped — dropping RAT quietly would change the
blueprint's meaning with nobody noticing.

## 6. Classroom grade

Assess now reads the selected classroom's real `gradeId`. A missing or
unrecognised grade produces a refusal naming the recorded value, **not
a Class 6 fallback**. Tested for Classes 5–8 and an out-of-scope Class
12.

## 7. Grade enforcement

Both must hold: the specification permits the grade **and** the item
does. A test narrows items to Classes 7–8 and confirms a Class 5
request fails even though the specification permits Class 5.

## 8. Versioned assignment and frozen form

`FormalGrowthAssignment` persists framework, specification, blueprint,
bank, language, router, reporting and support-policy versions, plus the
configuration snapshot.

**Frozen-form strategy (§12): Option A chosen.** The assignment stores
exact item IDs and order. Option B (deterministic reassembly from a
seed) was rejected because it reassembles per launch — a bank change
between two students in the same window could hand them different forms
while both records claim the same blueprint. Tested: pushing new items
into the bank does not alter an existing assignment. Item **IDs only** —
never stems — so secure content stays out of UI-visible metadata.

## 9. Assignment persistence

Real store with create / read-by-classroom / active-for-classroom /
cancel, separate from practice assignments. **Production still cannot
create one** — `createFormalAssignment` refuses without an authorized
framework and a ready form, proven by test. Fixtures inject
authorization rather than writing fake evidence into production data.

## 10. Student flow and formal session runner

The Growth Check card renders on Home **only** when a live assignment
exists for the student's classroom; no permanent tab is added. A
screenshot check confirms it is **invisible in production** and that
student copy carries **zero assessment jargon**.

`formalSessionRunner.ts` guarantees items come only from the frozen
form and in order — a response to any other item is refused — with
exposure recorded per administered item, plus response time, omissions,
interruptions and resume events.

**Resume (§11):** returns the identical session and form. There is
deliberately no code path from resume to the assembler. A 20-minute gap
is *recorded* as an interruption, never punished. Expired windows block
both start and resume.

Completion yields `field_test_response_data` with **no score field of
any kind** — a field test studies the instrument, not the student.

## 11. Constraint honesty (§15)

`BLUEPRINT_CONSTRAINT_ENFORCEMENT` classifies every specification field,
and tests assert the table matches behaviour:

- **Hard:** domain min/max, minimum length, `intendedGrades`, allowed
  formats, exposure ceiling, item grade range, enemy items, language.
- **Advisory:** target share, target length, **cognitive-demand
  targets**, **difficulty target**.

Cognitive demand is **not enforced in v0.58**, stated plainly rather
than implied: the pilot bank is too small for a demand distribution to
mean anything, and failing assembly on it would block for a reason
carrying no evidence. Author difficulty stays advisory because
enforcing it would manufacture false psychometric precision.
