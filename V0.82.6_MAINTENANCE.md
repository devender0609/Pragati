## §8 — what the next release should do, when responses arrive

Not implemented now. The existing `educatorReview.ts` import and
adjudication path already records per-response submissions against an
`expectedFingerprint` and an `expectedItemIds` list, so the current
system can receive a real response without new infrastructure. When one
arrives, the release should:

1. import the response against its review code, preserving reviewer
   identity, date and stated evidence;
2. check the response's fingerprint against the artifact it claims to
   review — a response to an older version is matched to that version,
   not silently applied to the current one;
3. adjudicate each finding individually: accept, revise, reject, or
   record as insufficient evidence;
4. revise content only where a finding is accepted, and bump
   `contentArtifactVersion` for any section that changes;
5. regenerate that section's fingerprint and package, and only that
   section's;
6. keep **sent ≠ reviewed** and **reviewed ≠ published** — publication
   stays a separate, explicit decision.

If a real response reveals something the import path cannot represent,
that is the moment to build more — not before.
