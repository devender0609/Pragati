## A. Root cause of the coordinate defect

Part I's section records were created from the **contents page**, whose numbers
are printed folios, and written into a field named `startPage` that the rest of
the system reads as a PDF page. Part II's were created later by locating
headings **inside the chapter files**, so they held PDF pages. Nothing caught it
because each set is internally consistent, the counts were never wrong, and no
test ever opened a PDF at a stored coordinate. The repair closes that: a test now
asserts every stored heading actually lies on the page it names.

## B. Coordinate model

`pdfStartPage` / `pdfEndPage` — 1-based positions inside the individual chapter
PDF. The **only** coordinates used for retrieval, ledger joins and evidence.
`printedFolioStart` / `printedFolioEnd` — the number printed in the book's running
head. A different system, allowed to be absent or to exceed a file's page count.
Every record carries `pageCoordinateBasis: PDF_PAGE`, and generated reports now
render "PDF p. 3 · printed p. 43" rather than one bare number.

**10 of 74** sections begin on a page with no printed folio at all — usually a
chapter opening — which is exactly why the two systems cannot be substituted.
