## B. Assumption audit — three failures, all confirmed in source

The v0.66–v0.83 review machinery was written for Fractions, where one section
meant one lesson. Three assumptions follow, and all three break on Class 9:

1. **`authoredSectionById()` searches only the Fractions chapter.** Every
   Class 9 artifact resolves to `null`, so `questionsForSection()` returns an
   empty array and `frozenCandidateFor()` returns `null`. Not one of the 92
   had a candidate.
2. **`sectionReviewCode()` derives the code from the section id**, splitting
   on `_s`. Chapter 9's lessons have no section id, so both would become
   `S??-…`; and eleven split sections would give two lessons one code.
3. **The question set asks the wrong book** — "is the notation the one a
   Class 6 student meets in Ganita Prakash?" A real question, aimed elsewhere.

Also confirmed: `REVIEW_BUILD` is pinned to v0.66.0 over five files, none of
which include data displays, the authored student route or the review
surface. And `ChapterReviewPreview` is Fractions-specific.

## C. Review identity — the artifact, not the section

Identity is `contentArtifactId` + version + **three separate fingerprints**,
generalising the sound part of the old design:

| Identity | Judges | Invalidated by |
|---|---|---|
| semantic | the mathematics and teaching | a content change |
| provenance | book, pages, sections, segments | a source correction |
| presentation (review build) | what was rendered | a renderer change |

Keeping them apart means a provenance correction does **not** discard a
pedagogy review, and a CSS change does not discard a judgement that 3/4 is
correct.

Codes read `C9-<artifact hash>-v<version>i<instrument>-<semantic prefix>`, e.g.
`C9-BC88B-v2i1-318A32`. **92 codes, 92 unique.**

## I. Reviewer surface

`Class9ReviewSurface` — chapters → lesson → the rendered lesson, through
`learnContentFor()` → `LearnSectionView`, **the same pipeline the student
route uses**. A reviewer judges what a student would see, not a second
rendering of the same words.

They see chapter, lesson, source, pages, objective, version, code and question
count. A test asserts `pragati_srcseg` and `officialSectionId` never reach the
screen; full machine identity lives in the export.

Review deliberately does **not** depend on student delivery eligibility —
gating review behind the student gate would make lessons unreviewable until
they were reviewed. `authoredLearnCatalogueForReview()` is separate, reached
only from review surfaces, and the student catalogue is unchanged.

## J. Response import — stale feedback cannot attach silently

A response carries the identity of what it judged, and import checks it:
unknown code, changed content, corrected provenance, version drift, instrument
drift, build drift, duplicate submission.

Quarantine is **informative, not binary**. A provenance correction reports
that the mathematics answers still apply; a build change invalidates only the
presentation-dependent answers and says the rest are unaffected.

Pragati's internal standard — stated as internal policy, not an external
requirement — is **two independent perspectives**: practising educator and
curriculum specialist. Coverage is tracked; nothing is declared reviewed
automatically, and disposition is the reviewer's own, never derived from
ticked boxes.
