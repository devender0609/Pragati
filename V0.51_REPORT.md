## 3. ItemSpecification architecture

`src/features/assessment/itemSpecification.ts`

Four things v0.50 conflated inside "ChapterBlueprint" are now distinct
types that do not interchange:

| Concept | What it is |
| :--- | :--- |
| **Competency** | What a student can do. Stable across textbook revisions. |
| **ItemSpecification** | The rules for writing an item that elicits evidence of one competency at one difficulty band. |
| **Item** | A concrete question authored from a specification. |
| **Blueprint** | How many items from which domains make a test. |

The schema carries all 28 required fields. Validation enforces the
rules that, if skipped, quietly produce a bad bank: an unstated
evidence claim, an inverted difficulty band, a select-format item with
no misconception targets, no stated prohibited shortcuts, a review
status with no named reviewer, field-test eligibility without expert
review, and any `calibrated` claim at all.

**The gate:** `requireSpecification()` refuses a Growth item that has
no `specificationId`, whose specification does not resolve, whose
specification is invalid, or whose `intendedUse` disagrees with the
item's `use`. Instructional items are deliberately exempt —
retro-specifying the existing practice bank would be busywork with no
measurement benefit.

## 4. Pilot rational-number specification set

`src/features/assessment/rationalNumberSpecifications.ts` — **eight
specifications**, not an item bank:

part-whole representation · number-line magnitude · equivalence ·
comparison/ordering · unlike-denominator operations · decimal
connection · ratio · percentage.

Each states what a correct response is evidence *of*, what an incorrect
response may *indicate*, the prohibited shortcuts (an item solvable by
elimination does not measure the competency), inappropriate cueing,
named misconception targets with distractor guidance, expected response
time, and its scoring rule.

**Every one is `draft`, with no reviewer, and none is field-test
eligible.** That is the accurate state, and validation enforces that a
review claim requires a named reviewer.

## 5. Readiness-status separation

`src/curriculum/readiness.ts` — four axes with **no inference between
them**. Growth readiness is never derived from item counts, because
having questions is not the same as having calibrated instruments.

The real Class 6 Fractions state, which one label could not express:

> curriculum `secondary_corroborated` · instruction `prototype` ·
> practice `usable` · growth `not_eligible`

`validateReadiness()` rejects any `calibrated` or `operational` Growth
claim outright. Students see only `studentAvailabilityLabel()`, which
answers "is there something here for me?" and is provably independent
of Growth status.

## 6. Learn / Practice / Growth separation

`src/features/assessment/growthSession.ts`

The separation is in the rules, not the UI. `GROWTH_RULES` disallows
instructional navigation, hints, worked examples, and immediate
correctness feedback, and requires exposure logging. `PRACTICE_RULES`
permits all of them, because practice claims nothing.

`buildGrowthPool()` refuses on any of: no secure items, an item without
a valid specification, or a bank smaller than the requested length.
There is no partial success — a compromised pool is not a smaller valid
pool. `assertNoLeak()` throws if a Growth item reaches Learn or
Practice.

Student navigation is unchanged at four tabs. Growth appears on Home
only when an assignment is live.

## 7. Growth administration prototype

`src/features/assessment/GrowthAdministration.tsx`

Teacher: class → testing window → accommodations → assign.
Student: Home card → instructions → begin → completion.

**The prototype's most useful behaviour is that it refuses.** Pragati
has no authored Growth items, so the panel shows the teacher why and
disables *Assign*, rather than sending students into an empty test.
Accommodations are recorded with an explanation that an accommodated
sitting may not be directly comparable.

Test length comes from the specification (**35 items, ~40 minutes**),
not the v0.50 ten-item assumption.

## 8. Growth reporting model

`buildGrowthReport()` returns items administered, correct responses,
competencies sampled, per-domain evidence, completion status, the fixed
status line *"Prototype diagnostic evidence — not yet psychometrically
calibrated"*, and explicit limitations.

There is deliberately **no `score`, `percentile`, `abilityEstimate`, or
`growth` field**. A field called `score` set to null eventually gets
rendered as 0; an absent field cannot. A test asserts the serialised
report contains no forbidden claim, and that an `AbilityEstimate`
passed in is ignored rather than leaked.

Domains below four administered items are marked
`sufficientForComment: false`, so the report declines to characterise
performance it cannot support.

## 9. Item-type architecture

`src/features/assessment/itemFormats.ts` — three real scorers
(single-select, numeric entry, fraction entry); eight future formats
declared but unimplemented.

**Unsupported formats fail safely.** `scoreResponse` returns
`unsupported_format` — never a boolean — because a fake score enters
the data as if it meant something. Two related traps are closed:
`Number('')` is 0, so a blank numeric entry is `invalid_response`
rather than a correct answer to 0; and fraction comparison uses
cross-multiplication, not floating point. Whether `2/4` is correct for
`1/2` depends on what the item asked, so the specification decides via
`requireLowestTerms`.

## 10. Student copy simplification

`src/curriculum/studentNames.ts`

The exact reported defect is fixed: `"Numbers & Addition (Class 1 —
starter)"` → **"Play with Numbers"**. `MODULE_LABELS` is untouched,
because teachers genuinely need `"(Class 12 · Ch 8)"` to locate content.

Curated names cover the starter modules; `stripInternalMetadata()` is
the fallback, so a module added later cannot leak `"(Class 9 —
starter)"` just because nobody curated it. A test sweeps **every**
module in the registry against the jargon list.

## 15. Recommended v0.52

1. **Human-verify Class 6** from the primary PDF. One person, twenty
   minutes, and it unblocks every downstream curriculum claim.
2. **Review the competency framework** against NCF-SE 2023 and PARAKH,
   then move `frameworkSourceStatus` off `draft_internal`.
3. **Author 2–3 items per pilot specification** — roughly 20 items —
   and put them through expert review. Enough to exercise the whole
   pipeline; far short of a bank.
4. **Wire the administration prototype into routing**, then screenshot
   the Growth flow at all five widths.
5. **Do the simplicity audit** deferred from this iteration.
6. **Resolve the Grade 7 contradiction** from the primary source, as
   the second proof-of-process case.

Item authoring at scale should wait until (1) and (2) are done —
authoring against an unverified framework produces material that has to
be re-reviewed later.
