# 0.84.0-rc.4 — checkpoint 47: release-documentation hardening

## I. Verdict — `CLASS_9_DEPLOYMENT_RC_LOCAL_VERIFIED_REMOTE_PREVIEW_PENDING`

No remote preview deployment was executed, so no stronger verdict is
available. The implementation is unchanged and still correct; what changed is
that the documentation now says only what was actually proved.

## A. Why the checkpoint-46 verdict was too strong

Checkpoint 46 claimed `CLASS_9_DEPLOYMENT_RC_PREVIEW_VERIFIED` while also
recording `REMOTE_PREVIEW_DEPLOYMENT_NOT_EXECUTED`. Those cannot both hold.

I had quietly redefined "preview verified" to mean a local `vite preview`,
which is not what the gate asks. A local preview proves the bundle runs on
this machine; it proves nothing about a deployed origin, its asset paths, or
storage behaviour on a different host. The correct state until a real remote
preview exists is **local verified, remote pending**.

## C. The bundle claim — corrected, and the correction goes further

The runbook said a public bundle "does not contain the route at all". **That
was false**, and I verified it against the shipped artifact rather than taking
the finding on trust. Inspecting `pragati-0.84.0-rc.3-public-safe-dist.zip`:

| Probe | In the public bundle |
|---|---|
| `VITE_ENABLE_AUTHORED_LEARN_PREVIEW` | present |
| "Internal preview" notice string | present |
| Lesson prose — "Ishango", "Brahmagupta", "gambler" | **present** |

So the correction is sharper than the finding stated. It is not only preview
*code* that survives — **the lesson text itself ships in the public
JavaScript**.

The guarantee is therefore stated exactly, in the source comment, the runbook
and the README:

> The public-safe build has authored-draft delivery disabled; the catalogue
> and direct lesson lookup deny those artifacts. This is inaccessibility, not
> absence.

**This is a delivery gate, not a confidentiality measure.** Anyone reading the
shipped assets can find the lesson text. If unreviewed content must also be
unreadable in the bundle, that requires a build-time exclusion, which this is
not and does not claim to be. I would rather name that limitation than let a
reader infer a protection that does not exist.

## Version rule, stated once

**Any change to packaged bytes gets a new version.** Documentation is part of
the package, so this is `0.84.0-rc.4` rather than an rc.3 repack. Two
different ZIPs will never share a version, and a hash always has exactly one
version behind it.
